# Examples

Three willed documents, one per file binding with a text-layer marker
carrier, each carrying the same two regions (a `keep` region around "The
approved sentence." and an `append` region around a one-line decision
log) so they are easy to compare across formats. Google Docs has no
example file — see `google-docs.md` for why.

All three were regenerated fresh for this `will/1` candidate
(2026-08-31): no copied parts, no stray `customXml`. The example content
itself is neutral — no company or product name appears anywhere inside
`willed.md`, `willed.docx`, or `willed.pdf`.

## willed.md

Authored directly, by hand, to the Markdown binding's placement rule
(MD18): each marker alone on its own line, self-closed, with a blank
line on each side.

- sha256: `2b507396730ccc32528f2f4151846b4089553a00fb419cc4c9fdd6beabb5a4ec`

## willed.docx

Generated by [`generate_docx.py`](generate_docx.py):

```sh
python3 generate_docx.py
```

Tested with **python-docx 1.2.0**. Each marker is one paragraph holding a
single hidden run (`w:vanish` on the run) with the paragraph mark itself
also hidden (`w:vanish` on `pPr/rPr`) — the dual-vanish frozen form
(WILL-1.md, "DOCX — hidden-text marker lines") — so a willed document
is layout-identical to its unwilled twin. python-docx's default template
carries an unused `customXml` bibliography-schema part; the script strips
it, along with its relationship and content-type entries, so nothing
stray ships. Zip-entry timestamps are pinned (matching the fixed date
already baked into `docProps/core.xml` by the template) so two runs of
the script produce byte-identical output.

- sha256: `8f8fbfec4630033234bd69afefb79305e4cecd8e76046d82de9cfd880a7529a5`

Validated: `python-docx` extracts all document text (markers included,
verbatim, in order); feeding that text to `reference/will.mjs parse`
yields **exactly 2 regions, 0 faults**. A `pandoc -t plain` round-trip
also recovers both marker pairs whole.

## willed.pdf

Generated by [`generate_pdf.py`](generate_pdf.py):

```sh
python3 generate_pdf.py
```

Tested with **reportlab 5.0.1**. This is the PDF binding's locked
engineered form (WILL-1.md, "PDF — non-rendering text-layer marker
lines"): each marker is one text object on one baseline, text rendering
mode 3 (invisible — unpainted by ordinary rendering, still present for
search/copy/accessibility/extraction), placed at **the same x column as
the body text it governs** (x=72, not a separate margin column), on a
**non-advancing boundary baseline** strictly between two visible lines —
a marker consumes none of the document's own vertical flow, so a willed
document's visible lines sit at exactly the same heights as its unwilled
twin's. Each marker is wrapped in its own `saveState()`/`restoreState()`
(PDF `q`/`Q`) — `Tr` persists in the graphics state across `BT`/`ET`, so
without this the invisible mode would leak into the ordinary text drawn
right after a marker. The marker font is **embedded, subsetted DejaVu
Sans** (not a base-14 WinAnsi font): the binding requires a lossless
`ToUnicode` mapping for every scalar a marker's intent may contain, and
Helvetica's fixed WinAnsi encoding cannot represent one outside Latin-1
at all — it does not merely render wrong, it *extracts* wrong.
`invariant=1` pins reportlab's own timestamp/ID fields so the script is
reproducible. (Why this form looks like this, not an earlier one: git
history and WILL-1.md's own PDF binding section, not restated here.)

**The example's identity is the CONTENT-STREAM sha256, not the file
sha256.** `verify_pdf.py` strips the invisible marker text objects out
(the same method the layout-identity proof below uses) and prints the
sha256 of what remains — the visible body text, drawn in the base-14
Helvetica font that is never subsetted. That is the pinned invariant, the
one CI gates on, and the one a reviewer should compare:

- willed.pdf content-stream sha256 (markers stripped): the value
  `verify_pdf.py` prints — `3be5753f…` at the locked form; the file is
  the identity only through this stream.

The whole-file hashes below are **snapshots of one font package**, not
the example's identity: a different `fonts-dejavu-core` version can
legitimately subset the embedded marker font differently (a different
glyph set, a different internal glyph ordering) without changing anything
this binding governs, since that subset lives entirely inside the
*invisible* marker text objects. An outside reviewer regenerated this
file with the same reportlab 5.0.1 and a different DejaVu package and
watched the whole-file hash move while the stream pin held; that is the
expected behaviour, not drift.

- willed.pdf whole-file sha256, this environment's snapshot:

### The acceptance battery

[`verify_pdf.py`](verify_pdf.py) is the executable proof; run it with
`python3 verify_pdf.py`. It asserts, per required extractor — `pypdf
6.16.2` and `pdfminer.six 20260107` always, plus `pdftotext` (Poppler,
`-raw` mode) when installed, folded into the same per-extractor checks
below rather than run separately:

- **exactly two regions, zero faults**, from each extractor's own text,
  in reading order, on every extractor tested (WILL-1.md's PDF binding
  section documents why an earlier carrier form failed this).
- the **keep** region's governed text is exactly `The approved sentence.`
- the **append** region's governed text is exactly the decision-log line
- **structural layout identity**: the willed page's own content stream,
  with its invisible marker text objects stripped out, is byte-for-byte
  equal to the unwilled twin's content stream. This is a stronger proof
  than a pixel comparison — two content streams that are byte-identical
  render identically by construction, and the method is exact rather
  than tolerance-based. (Method: every marker is individually wrapped in
  its own `q`/`Q` and is the only thing that sets render mode 3, so the
  blocks matching `` q\n...3 Tr...\nQ\n `` are exactly the marker text
  objects; removing them and nothing else isolates the visible
  operations. See `_strip_marker_objects()`.)
- a **mixed-script intent** — Latin, a genuinely decomposed combining
  mark (`café` normalized to NFD, base `e` + U+0301), CJK (via a second
  embedded font, WenQuanYi Zen Hei, switched to mid-object without moving
  the baseline), and right-to-left text (Hebrew, Arabic) — recovers
  **byte-for-byte** through every required extractor, each asked for
  logical-order extraction (`pypdf`: `extraction_mode="layout"`) — see
  WILL-1.md's PDF binding section for why discovery holds only under
  logical order, and "What this rig could not prove" below for what
  happens when a reader asks for visual order instead.
- a **maximal 512-Unicode-scalar-value intent** (exactly 512 scalars, not
  UTF-16 units or bytes, mixing the same Latin/combining/CJK/right-to-left
  pool) stays **one carrier unit** (one region, zero faults, from both
  extractors), measures **298.8pt wide at 1pt** against **540.0pt** of
  usable width from x=72 to the US Letter page's right edge (612pt page
  width) — comfortably in bounds — and recovers **losslessly**.

### What this rig could not prove

Run and reported by `verify_pdf.py`, but **not** part of the gating
battery and **not** claimed as proven:

- **Astral-plane scalars** (Unicode code points above U+FFFF — most
  emoji, several historic scripts) do not round-trip in this rig. The
  cause is a reportlab 5.0.1 defect, not a carrier defect: its TrueType
  embedding (`reportlab/pdfbase/ttfonts.py`, `makeToUnicodeCMap()`)
  writes every code point through a fixed `"<%02X> <%04X>"` format —
  four hex digits, a Basic-Multilingual-Plane assumption — with no
  UTF-16BE surrogate-pair encoding for anything above U+FFFF, and
  `TTFont` embeds only 256-glyph "simple" font subsets, never a
  composite Type0/CID font. The symptom is exact and reproducible: a
  marker containing U+1F600 writes a malformed `ToUnicode` CMap entry
  (`<01> <1F600>`, five hex digits — neither a valid BMP form nor a valid
  surrogate pair), and both extractors then either drop the character
  (`pypdf`) or recover the wrong one (`pdfminer` reads the truncated hex
  as U+1F60, a different, real BMP character). Fixing this needs either
  an upstream reportlab fix or a writer that embeds a proper Type0/CID
  composite font; neither is in this rig. The binding's `ToUnicode`
  requirement is normative regardless — this is a gap in one writer
  library's current output, not a relaxation of the law.
- **Poppler (`pdftotext`)** is not installed in this environment, so it
  is not exercised at all — not run, not assumed to pass, not counted.
  Neither extractor this battery *does* run is Poppler-based. Where
  installed, it participates as a required extractor above, in `-raw`
  (logical-order) mode.
- **pypdf's DEFAULT (visual-order) extraction mode**, on the identical
  right-to-left marker the mixed-script case above proves round-trips
  under the required `layout` mode, does **not** recover the marker at
  all: pypdf's default reorders the bidirectional opener line before
  this reader ever sees it, scrambling the marker's own grammar, so
  `parse()` correctly reports it unpaired rather than a region. This is
  not a rig limitation to fix — it is the documented reason WILL-1.md's
  PDF binding requires logical-order extraction for discovery in the
  first place: a visual-order projection's loss, never this carrier's.
  See `_rtl_default_mode_probe()`.
- **Acrobat Save As** and the named rewrite hops (Ghostscript, qpdf) are
  not re-run against this specific locked form in this rig. (Prior-form
  evidence only: those survival claims describe the marker-survival
  property of text rendering mode 3 in general, verified against the
  prior carrier form, not a re-execution against these exact bytes.)

## Regenerating and re-validating

```sh
cd examples
python3 generate_docx.py
python3 generate_pdf.py
python3 verify_docx.py
python3 verify_pdf.py
node ../reference/will.mjs parse willed.md
python3 -c "import docx; d=docx.Document('willed.docx'); print('\n'.join(p.text for p in d.paragraphs))" | node ../reference/will.mjs parse -
python3 -c "import pypdf; print(pypdf.PdfReader('willed.pdf').pages[0].extract_text(extraction_mode='layout'))" | node ../reference/will.mjs parse -
```

`-` reads fd 0 (stdin) portably via `will.mjs`'s own CLI, with no
dependence on a platform actually exposing a `/dev/stdin` filesystem
entry.

The two `will.mjs parse` lines should each report `faults: []` and
exactly two `regions`; `verify_docx.py` and `verify_pdf.py` should each
report `0 failing assertion(s)`.
